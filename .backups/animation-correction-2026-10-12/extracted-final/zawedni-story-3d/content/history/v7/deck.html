ZAWEDNI est une startup tunisienne, créée avec Hadil Ben Masseoud et installée à la pépinière d'entreprises de Mahdia.

Elle propose un service qui relie l'achat local à une démarche de responsabilité sociétale des entreprises, ou RSE. Le projet comprend la plateforme web et mobile, puis les moyens de la déployer, de protéger ses données et de suivre son fonctionnement.

Cette organisation permet d'appliquer une règle importante. Le fournisseur envoie la grille d'évaluation de son entreprise. Le serveur l'enregistre, puis l'administrateur l'examine et valide sa décision.

Quand le fournisseur demande l'accès à une fonction du marché concernée, le serveur vérifie cette décision. Si la grille est approuvée, l'accès est autorisé. Sinon, la demande est refusée. La règle reste donc appliquée côté serveur, même si l'utilisateur passe directement par l'API.

Une question se pose maintenant : comment mettre une nouvelle version en ligne, réduire les erreurs et protéger les données ? C'est le rôle de l'approche DevSecOps. On commence par l'environnement qui accueille l'application.

Architecture et démarche DevSecOps · Outils

Outils d'infrastructure

Docker

Azure

ACR

Conserver les images

Versions identifiables, accessibles au cluster

AKS

Exécuter les conteneurs

Kubernetes géré par Azure : redémarrage et mises à jour

Terraform

Décrire les ressources Azure : cluster, registre, stockage

Infrastructure versionnée et reproductible

Pour cet environnement, on utilise quatre outils complémentaires. Docker prépare une image qui contient le service et ce qu'il faut pour l'exécuter. ACR, le registre, conserve ces images. AKS les utilise pour faire tourner les services dans un cluster, c'est-à-dire un groupe de machines. Terraform décrit les ressources Azure dans des fichiers. On peut ainsi retrouver la configuration et reproduire l'environnement sans tout régler à la main.

Architecture et démarche DevSecOps · Démarche

Le cycle DevSecOps

Sécurité : analyses avant publication · accès protégés au déploiement · surveillance pendant l’exploitation

Ces outils forment un cycle continu. À gauche, on prépare une modification, on écrit le code et on le teste. À droite, on déploie et on observe le service.

Un problème détecté conduit à une correction du code. La sécurité accompagne le cycle : contrôle du code, protection des accès et surveillance. Ce lien entre développement, sécurité et exploitation forme l'approche DevSecOps.

EXEMPLE DE DEMANDE

Plusieurs sites utilisent la même adresse IP publique. L'Ingress reçoit la demande et choisit le bon service.

Il regarde d'abord le nom du site : le nom client mène au site client, et le nom admin au site d'administration.

Chaîne CI/CD · Vue d'ensemble

Notre chaîne de livraison

Cette chaîne organise une nouvelle version.

On enregistre la modification dans GitHub.

GitHub Actions lance les tests et les analyses. Si la publication est autorisée et les contrôles passent, l'image est envoyée dans ACR.

Le pipeline change le manifeste : le fichier qui indique quelle image utiliser. ArgoCD applique cette version dans le cluster.

Chaîne CI/CD · Pipelines

Organisation des dix pipelines

La chaîne comporte dix pipelines.

Cinq suivent les composants : backend, client web, administration, IA et mobile. Les chemins modifiés indiquent quel composant reconstruire.

Les autres portent sur des contrôles communs, comme les secrets ou l'infrastructure. Cela évite les reconstructions inutiles et facilite la recherche d'une étape en échec.

Il y a deux moments à distinguer.

Avant la fusion, on ouvre une pull request : une demande pour intégrer le changement. Les contrôles s'exécutent, mais aucune image n'est publiée.

Après la fusion, le push déclenche les étapes de livraison prévues. Si les contrôles passent, l'image est publiée et le manifeste est mis à jour.

Staging reçoit la version de test ; main sert à la production. Pour le mobile, le résultat est un APK distribué par Azure Blob.

Que vérifient les tests ?

COMPORTEMENT ATTENDU

Une règle métier

L’entreprise A tente de modifier un employé de l’entreprise B.

Attendu : modification refusée, données inchangées.

RÉSULTAT DU TEST

Une comparaison

Le test prépare ce cas, puis compare le résultat obtenu au résultat attendu.

Exemple réel : EmployeeServiceOwnershipTest, API Java.

EFFET SUR LA LIVRAISON

Continuer ou arrêter

Résultat conforme : le pipeline continue.

Test en échec : la publication s’arrête.

  • JUnitAPI Spring Boot
  • Vitestsite client
  • pytestservice d’IA
  • flutter testapplication mobile

Les deux issues montrent le rôle du test dans la chaîne ; ce n’est pas une nouvelle exécution.

Avant de publier, on vérifie le comportement du code avec des tests automatiques. Par exemple, une entreprise ne doit pas modifier un employé d'une autre entreprise. Le test prépare ce cas et vérifie que la modification est refusée.

Si le résultat correspond à la règle, le test passe. Sinon, il échoue et la publication s'arrête.

Chaîne CI/CD · Contrôles

Quels contrôles arrêtent la livraison ?

Arrête le pipeline

le job échoue, rien n'est publié

  • Gitleaksun secret est trouvé
  • Dependency-Checkfaille de score CVSS 9 ou plus
  • Trivyfaille HIGH ou CRITICAL qui a un correctif ; 2 exceptions datées
  • SonarCloudquality gate, sur PR et main seulement

Signale seulement

un rapport à lire, le job continue

  • Semgreples résultats ne font pas échouer le job
  • Checkovanalyse marquée non bloquante

Protège la fusion

rôle de GitHub, pas des outils

  • Protection de brancherègle de GitHub, distincte des pipelines
  • État actuelnon activée ; prévue dans les perspectives

Ces outils ne produisent pas tous le même effet. Gitleaks, Dependency-Check, Trivy et SonarCloud peuvent arrêter le pipeline selon les critères configurés.

Dans cette configuration, Semgrep et Checkov signalent les problèmes sans arrêter la livraison.

La fusion dans GitHub dépend d'une autre règle : la protection des branches.

La supervision utilise trois types d'informations.

Les métriques donnent des mesures, comme la mémoire ou le nombre d'erreurs. Prometheus les collecte et Grafana les affiche.

Les journaux décrivent les événements de l'application. Alloy les collecte, Loki les conserve et Grafana permet de les consulter.

Si une mesure dépasse un seuil configuré, Prometheus déclenche une alerte et Alertmanager envoie la notification.

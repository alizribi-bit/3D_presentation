Architecture · Le choix

GitHub Actions automatise les contrôles ; AKS héberge les services

On a fait deux choix.

Pour les tests et les constructions, GitHub Actions : le dépôt est déjà sur GitHub, et on n'a pas de serveur CI à entretenir.

Pour exécuter les services, AKS : Azure gère Kubernetes, et on dispose du crédit étudiant. Ces choix répondent aux besoins du projet.

Architecture · DevSecOps

DevSecOps place les analyses de sécurité dans le pipeline, à chaque changement

Pour la sécurité, on a suivi l'approche DevSecOps.

Souvent, la sécurité arrive à la fin, quand corriger coûte cher.

Ici, les analyses sont dans le pipeline : chaque changement est vérifié automatiquement, comme un test.

Architecture · Vue d'ensemble

La chaîne a trois zones : le poste, GitHub et Azure

Voici l'architecture en une image.

Sur le poste du développeur, on code et on pousse le commit vers GitHub.

Dans GitHub Actions, le pipeline teste, analyse et construit les images.

Dans Azure, ArgoCD déploie sur le cluster Kubernetes, et Prometheus et Grafana le surveillent. Prenons chaque brique, avec la raison du choix.

Architecture · Docker

Docker met chaque service serveur dans une image qui tourne partout

Pour que le code tourne de la même façon partout, on utilise Docker.

Chaque service serveur devient une image, avec tout ce qu'il faut pour le lancer. Docker Compose lance toute la plateforme en local.

L'image du service d'IA dépassait quatre gigaoctets ; avec PyTorch en version CPU, elle passe à 928 mégaoctets. Le mobile, lui, produit un APK.

Architecture · Environnements

Le cluster prévoit deux environnements : staging est déployé, la production est seulement configurée

Kubernetes organise les conteneurs : il les lance, les relance et les relie. AKS est le service Kubernetes géré par Azure.

Dans le cluster, deux environnements sont prévus, séparés par des namespaces, c'est-à-dire des espaces logiques. Staging est déployé, et c'est lui qu'on a testé. La production est décrite dans la configuration, mais elle n'est pas déployée sur le cluster actuel.

Parcours d'un changement · Le chemin prévu

Le chemin prévu d'un changement passe par develop et staging avant main

Suivons un changement sur le chemin prévu.

Sur une branche feature, on ouvre une pull request vers develop : Semgrep fait une première analyse, sans construire d'image.

Une pull request vers staging lance les contrôles liés aux fichiers modifiés. Après la fusion, la version arrive en staging, et on la teste.

La pull request vers main mènera à la production : cette étape est prévue, pas encore réalisée.

Parcours d'un changement · Les pipelines

Cinq pipelines suivent un composant chacun, cinq autres vérifient tout le dépôt

Dix pipelines existent.

Cinq suivent chacun un composant, grâce aux filtres de chemins. Sur une pull request vers staging, une modification du backend lance son pipeline. Des contrôles communs au dépôt peuvent s'ajouter.

Les cinq autres vérifient tout le dépôt : les secrets, le code, l'adresse publique, l'infrastructure et les workflows.

Parcours d'un changement · Règle d'équipe

Sans protection de branche, un pipeline rouge n'empêche pas la fusion

Pipeline rouge = un échec

Un contrôle a trouvé un problème. Le job s'arrête, rien n'est publié.

Fusion interdite = protection de branche

Absente ici : offre gratuite de GitHub, dépôt privé.

Règle d'équipe : on ne fusionne pas tant que c'est rouge.

Un pipeline rouge signale un échec, mais il n'interdit pas la fusion.

Pour cela, il faut une protection de branche, que l'offre gratuite de GitHub ne donne pas pour un dépôt privé. On applique donc une règle d'équipe : on ne fusionne pas tant que c'est rouge.

Contrôler et publier sont deux choses différentes.

Une pull request lance les contrôles liés aux fichiers modifiés. Elle peut construire et scanner une image, mais elle ne publie rien.

Après la fusion, si un composant a changé, le push sur staging publie sa nouvelle image et met à jour son manifeste. Exemple, le 6 octobre : la pull request 19 ne touchait que la configuration du cluster. Ses contrôles ont tourné, sans construire d'image.

Le rapport parle de StatefulSet ; dans les fichiers, c'est un Deployment avec ce volume.

La base PostgreSQL 16 tourne dans un seul pod, avec un volume persistant de cinq gigaoctets sur un disque Azure. Si le pod redémarre, les données restent. Leçon des sprints

Pour les mises à jour de l'application, tout passe par le manifeste dans Git, puis par ArgoCD. Revenir en arrière voudrait dire faire un git revert : sur staging, chaque image a son identifiant dans Git, donc c'est possible, mais ce n'a pas été testé. Ce qui tourne dépend de l'événement. Sur un push vers une branche feature ou develop, les workflows démarrent, mais leurs jobs sont sautés ; seuls les guards tournent si les workflows ou k8s changent. Une pull request vers develop lance Semgrep, et le mobile si ses fichiers changent. Une pull request vers staging ou main lance les contrôles des composants touchés et les contrôles transversaux : l'image peut être construite et scannée, mais rien n'est publié. Le push sur staging publie l'image avec l'identifiant du commit et met à jour le manifeste. Sur main, le même mécanisme est prévu, mais pas encore démontré. Les trois essais réels sont log4j, un faux secret et une ancienne adresse publique.

Sur une pull request, l'APK reste un artefact GitHub. Sur un push, il est aussi envoyé dans le stockage Azure, avec la date et l'identifiant du commit dans son nom, puis un e-mail part. L'envoi vers Google Drive ne bloque pas le pipeline : son étape est verte, mais cela ne prouve pas que le fichier est arrivé.
